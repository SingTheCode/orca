2026-10-20 · 대상 ~/dev/orca (fork SingTheCode/orca) · 서버 ~/dev/spec_flow 로컬 구동

Orca에 없고 가치가 큰 SpecFlow 기능 8개를 Orca에 붙이는 계획입니다. SpecFlow 서버는 로컬에 띄워 두었고, Orca는 그 서버의 API를 쓰는 클라이언트 화면과 연동을 추가합니다. SpecFlow의 Go 로직과 프롬프트를 다시 짜지 않고 그대로 쓰는 것이 핵심입니다.

3. 구조

설계 결정

결정이유
SpecFlow 서버를 그대로 쓰고 Orca는 클라이언트만 만든다프롬프트, 버전 관리, WBS 일정 계산, ERD 이름 규칙 검사가 Go에 이미 있고 로컬에서 동작을 확인했다. TS로 다시 짜면 두 벌이 된다.
HTTP와 토큰은 main 프로세스에서만 다룬다Orca Jira와 같은 방식(src/main/jira/*, integration-credential-file.ts). renderer에는 토큰을 넘기지 않는다.
Jira 게시는 Orca의 Jira 연결을 쓴다사내 Jira PAT가 이미 Orca에 있다. SpecFlow의 Jira 설정·자격 증명을 또 등록하지 않는다.
작업 실행은 omp + SpecFlow MCPSpecFlow의 자동 개발(서버에서 Claude 실행)은 쓰지 않는다. omp가 MCP 도구로 작업을 받고 결과를 올린다.
인터뷰는 omp의 grill-me 스킬사용자 결정: SpecFlow 인터뷰 채팅 대신 grill-me를 기본으로 쓴다. 질문은 omp 세션에서, 명세 생성과 버전 관리는 서버에서 한다. 서버 인터뷰 API(interview/*)는 Orca에서 호출하지 않는다.
ERD는 reactflow로 편집사용자 결정: 편집까지 필요. 서버 ERD JSON이 이미 reactflow 노드·간선 형식이라 그대로 읽고 쓴다. @xyflow/react 의존성을 추가한다.
SpecFlow 프로젝트와 Orca 저장소를 1:1로 연결연결 정보(서버 URL, 저장소 → 프로젝트 ID)는 GlobalSettings에, 계정 비밀번호와 토큰은 암호화 파일에 둔다.
서버 URL은 설정값사용자 결정: 추후 공용 서버를 두고 관리자가 팀 ID로 묶어 관리한다. 클라이언트는 서버 URL만 바꾸면 공용 서버로 옮겨 가도록 만든다. 팀 모델은 서버 쪽 별도 작업.

4. 단계별 계획

단계내용완료 기준공수(추정)
P0 기반main SpecFlow 클라이언트(로그인, 401 시 refresh 후 재시도, 1시간 refresh 만료 시 재로그인), 자격 증명 암호화 저장, 설정 카드(서버 URL·계정·연결 테스트), 저장소 ↔ 프로젝트 연결/생성, 빈 SpecFlow 페이지와 탭 골격설정에서 연결 테스트 성공, 현재 저장소에 SpecFlow 프로젝트를 만들거나 연결4~5일
P1 인터뷰·명세 (F1, F2)"grill-me로 기획" 버튼: omp를 plan mode + /skill:grill-me로 실행, SpecFlow MCP 연결. 서버에 submit_grill_decisions MCP 도구와 엔드포인트 추가. PRD/TRD 보기·편집, 버전 목록과 비교, 추가 답변으로 다듬기grill 세션 종료 후 PRD/TRD v1이 생기고, 편집 저장 시 v2가 생기고 diff로 비교4~5일
P2 WBS (F3, F4)WBS 생성, 우선순위·선후관계·일정 표시, 작업 편집·삭제, 하위 작업 AI 생성, 대화형 작업 제안 → 확인 → 생성, SSE 갱신생성한 작업이 즉시 목록에 반영되고, 다른 곳에서 바꾼 상태가 SSE로 갱신4~6일
P3 Jira 게시 (F5)작업 선택 → 이슈 유형·Epic 지정 → 미리보기 → Orca Jira로 순차 생성, 결과(키·URL·실패 사유) 표시, SpecFlow 작업에 Jira 키 기록사내 Jira에 이슈가 생기고, 다시 게시하면 이미 연결된 작업은 건너뜀3~4일
P4 에이전트·검증 (F6)프로젝트별 MCP 키 발급(JWT API), omp 세션에 SpecFlow MCP 서버 연결, 작업 상세의 "omp로 실행"(작업 프롬프트를 agent.launch로 전달), 검증 리포트 목록 표시omp가 작업을 받아 수행하고 submit_task_result로 올린 결과가 작업 상세에 표시3~4일
P5 ERD (F7)ERD 생성, reactflow 캔버스 편집(테이블·컬럼 추가·수정·삭제, 관계 연결, 위치 이동), 저장, 이름 규칙 위반 표시, DDL 보기·복사편집 후 저장하면 다시 열어도 유지되고 DDL에 반영5~6일
P6 코드 그래프 (F8)워크트리 소스를 zip으로 묶어 업로드(node_modules 등 제외), 분석 상태 표시, 개요·진입점·핵심 파일·검색·호출자/피호출자, AI 설명, 노드에서 Orca 에디터로 파일 열기현재 저장소 분석 후 함수 검색 → 호출 관계 → 파일 열기까지 동작4~5일

합계 약 27~35인일 (1인 기준 6~7주). P0 이후 P1·P2·P5·P6은 서로 독립이라 병렬 진행이 가능하고, P3은 P2, P4는 P2 뒤에 진행합니다.

5. 위험과 제약

항목내용대응
긴 LLM 호출PRD/TRD 약 2분, WBS·ERD 약 1분. 모두 동기 요청이고 진행률이 없다.main에서 타임아웃을 넉넉히(10분) 두고, 화면에는 진행 중 상태와 취소 대신 "백그라운드에서 계속" 표시

MCP 키 범위sf_mcp_ 키는 /api/v1/mcp/*만 쓸 수 있고 프로젝트 하나에 묶인다.Orca 화면은 JWT, omp 에이전트는 MCP 키로 역할을 나눈다
코드 그래프 범위Go와 JS/TS만 분석한다(JS/TS는 정규식 기반). zip 업로드는 20MB 제한.제외 규칙으로 크기를 줄이고, 지원 언어를 화면에 명시. 대형 저장소는 로컬 분석(Runner 경로) 이식을 별도 검토
Jira 키 기록SpecFlow 작업 모델에는 jira_ticket_key, jira_issue_id, jira_url, jira_synced_at가 있지만, 작업 수정 API 입력(UpdateTaskInput)은 이 필드를 받지 않는다(확인함).P3에서 SpecFlow에 "Jira 연결 기록" 엔드포인트를 하나 추가하거나 UpdateTaskInput에 필드를 연다. 서버 변경 1건
서버 위치지금은 개인 PC 로컬 서버라 팀 공유가 안 된다.추후 공용 서버 + 관리자의 팀 ID 관리(서버 별도 작업). 클라이언트는 서버 URL 설정만 바꾸면 된다
plan mode와 MCP확인함: omp plan mode에서도 MCP 쓰기 도구가 호출된다(add_task_note 성공, 2026-10-20).grill 세션 안에서 바로 결정을 제출한다

6. 결정 사항 (2026-10-20 확정)

  • 인터뷰: SpecFlow 인터뷰 채팅 대신 grill-me 스킬을 기본으로 쓴다.
  • ERD: 편집까지 지원한다(reactflow).
  • 서버 운영: 추후 공용 서버를 두고 관리자가 팀 ID로 묶어 관리한다. 지금은 로컬 서버로 개발한다.
  • 순서: P0 → (P1, P2, P5, P6 병렬) → P3, P4.
